# Node / Java MS Project XML field inventory

Issue #137 comparison. This inventory records the currently modeled XML surface in the Node and Java legacy codecs. It does not claim support for every field in the MS Project XML schema. A field absent from these tables is not preserved by either codec unless a later section says otherwise.

## Scope and interpretation

- Node sources: `src/ts/types.ts`, `src/ts/msproject-codec.ts`, `src/ts/msproject-xml-dom.ts`, and `src/ts/msproject-calendar.ts`.
- Java sources: `src/main/java/jp/igapyon/mikuproject/model/*Model.java`, `msprojectxml/MsProjectCodec.java`, `MsProjectXml.java`, `MsProjectXmlDom.java`, and `MsProjectCalendar.java`.
- “Both” means a modeled field is read and written by the legacy codec in each runtime. It does not mean byte-identical XML, identical defaults, or preservation of unknown elements.
- The classifications used below are: **equivalent** for the same modeled XML value/meaning, **implementation difference** for observable representation or conversion differences, **explicitly excluded** only where a source or contract says the field is intentionally unsupported, and **intent unclear** where the code drops data but no intent was found.

### Project conversion and unset behavior

- `textContent` trims XML text in both implementations. Date-like Project values are stored as strings; no date object or timezone conversion occurs in these field mappings.
- Node `parseNumber` uses JavaScript `Number` and accepts finite fractions/large values. Java `parseNumber` uses `Integer.parseInt`; Project numeric fields modeled as `Integer` therefore have an integer/range boundary. On invalid input both helper families use their fallback, but Java's integer parser and Node's number parser accept different lexemes. This is an **implementation difference**; no shared numeric precision/range contract was found.
- Optional empty strings map to `undefined` in Node where the codec uses `|| undefined`, and to `""` in Java text fields. Optional numeric/Boolean values map to `undefined` in Node and null Java wrappers. Collections are initialized as empty arrays/lists in both. Export omits empty/null optional scalar values; booleans serialize as `1` / `0` in both helpers.
- Both public XML import/export wrappers normalize the model and ensure a default calendar. That transformation is recorded under Calendar; it is not a Project-field omission.
- The Node round-trip fixture `tests/mikuproject-msproject-xml-roundtrip.test.js` covers Project metadata and scheduling fields, including OutlineCodes, WBSMasks, and ExtendedAttributes. Java `MsProjectXmlTest.importFromXmlReadsProjectCoreFields` covers the corresponding metadata and nested structures. Shared upstream `testdata/minimal.xml`, `hierarchy.xml`, and `dependency.xml` are also consumed by both suites, but the richer metadata cases are separate fixtures.

No Project field requiring a product change was identified in this inventory. Differences in unset representations and numeric conversion remain classified as implementation differences; loss of unmodeled XML remains intent unclear. No production source was changed.

### Task reference, ordering, and fixture notes

- Task records and repeated nested values are appended in XML document order by both codecs. Export iterates the model lists in order. No sort or parent reconstruction is performed in these codec methods.
- `CalendarUID` and `PredecessorUID` remain string references; XML import itself does not resolve them. Both validators check calendar references. Node first builds the complete Task UID set and then checks predecessor links. Java adds each UID while validating that Task and checks its predecessor links in the same loop, so a link from an earlier list item to a later Task can be diagnosed as missing (**implementation difference**). The intended treatment of forward references is not stated in the codec contract and is a DEC-10 decision input.
- Java's native workbook schema adds the Task columns `Type`, `Priority`, `ConstraintType`, `ConstraintDate`, and `Deadline` relative to the Node workbook schema. These are workbook-column extensions; Node's XML `TaskModel` and XML codec also read/write those XML tags. Workbook/XLSX extension ownership is separate from XML codec coverage. The XLSX `Notes`/`CalendarUID` header-position issue observed in LEG-J16 is likewise not evidence of XML Task-field loss.
- The Node fixtures include `round-trips task and assignment cost fields`, `round-trips task deadline and variance fields`, and `round-trips extended task work fields`, plus shared `hierarchy.xml` and `dependency.xml`. Java `MsProjectXmlTest.importFromXmlReadsFirstCutEntities`, `exportToXmlWritesFirstCutEntities`, `exportThenImportPreservesDirectChildExtendedStructures`, and the shared hierarchy/dependency fixtures cover corresponding task structures.
- No explicit unsupported-tag policy or one-field preservation requirement was found for unmodeled Task elements. Missing/default scalar and numeric differences are observed from the current codec/model implementation; their desired common contract remains undecided.

No Task implementation is proposed from this mapping alone. No production source was changed.

### Calendar order, references, defaults, and workbook relationship

- Both codecs iterate Calendar, WeekDay, WorkingTime, Exception, and WorkWeek elements in source order and export model lists in their current order. Node locates the first matching containers with descendant `getElementsByTagName`; Java's `MsProjectXmlDom` uses direct-child lookup for collection containers. For normal direct-child MSPDI structure they select the same data; malformed/nested duplicate containers could be treated differently (**implementation difference**, no fixture found).
- `Project.CalendarUID`, `Calendar.BaseCalendarUID`, `Task.CalendarUID`, and `Resource.CalendarUID` are retained as strings and validated after parsing. Both validate Project/Task/Resource calendar references against known Calendar UIDs; a missing BaseCalendarUID target and a self-reference are warnings. Neither XML reader rewrites existing references.
- Both public XML import wrappers normalize and add a `Standard` calendar when the project has no calendars, set Project.CalendarUID to the generated UID, use Monday–Friday working days with the configured/default working times, and generate Japanese holiday exceptions over the project date range. The default UID allocator's Java trimming and Node string conversion do not differ under this call path because allocation is reached only when the calendar list is empty. Calendar defaulting is a model normalization step, not an XML field read.
- The two calendar-default implementations use different date libraries for parsing date-only Project bounds (Node local `Date`, Java `LocalDate`) and different whitespace fallback expressions for direct model time values. Invalid dates, timezone boundaries, and whitespace-only in-memory time values were not covered by the inspected fixtures; exact edge behavior is **intent unclear** and should not be generalized from the shared normal cases.
- The workbook `Calendars` sheet represents calendars and reports counts for WeekDays, Exceptions, and WorkWeeks. The separate `NonWorkingDays` sheet flattens Calendar Exceptions into indexed rows (`CalendarUID`, `Index`, name/date boundaries, DayWorking). It is a projection of exceptions, not a replacement for nested XML WeekDays, WorkingTimes, Exceptions, and WorkWeeks; the workbook rows do not encode all nested schedule detail.
- Node fixtures `round-trips calendar base and weekday fields` and `round-trips calendar exceptions and workweeks` cover these structures; `warns when calendar baseCalendarUID points to itself` covers a reference warning. Java `MsProjectXmlTest.importFromXmlReadsCalendarStructures`, `exportToXmlWritesCalendarStructures`, and `ensureDefaultProjectCalendarBuildsJapaneseHolidayExceptions` cover the corresponding paths. Shared hierarchy/dependency fixtures are also used by both suites.

All mapped Calendar structures have read/write paths in both codecs. The inventory identifies representation/path differences and unknown-tag loss but no field uniquely absent from one implementation. No production source was changed.
